SUTD PML Team 2 · Early sepsis warning · PhysioNet 2019

From an hourly ICU chart to a sepsis risk score

Training and prediction use the same function to turn raw hourly rows into features. The model never sees raw rows. It sees one row of 276 numbers per hour, each built only from that stay's hours up to now.

1 row per patient per ICU hour 34 measurements + 4 static fields in 276 features out 6 h window · 0.2 false alerts per non-septic patient-day

How the API knows hours 1 to 7 when hour 8 arrives

The API keeps no memory between requests. The hospital's chart system already stores the stay, so each hour it sends the whole stay so far. The answer for hour 8 is the last hour of that request.

06:00 request
h1h2h3h4h5h6
07:00 request
h1h2h3h4h5h6h7
08:00 request
h1h2h3h4h5h6h7h8

Dark cell: the new hour. Scoring hours 1–8 gives the same hour-8 answer as replaying the whole stay, because hour t only uses hours up to t.

The request format built

POST /score   (or /predict with "stays": [...], up to 64)
{ "patient_id": "bed-4",
  "hours": [
    {"ICULOS": 1, "HR": 88, "Age": 67, "Gender": 1, "HospAdmTime": -5},
    {"ICULOS": 2},
    {"ICULOS": 3, "HR": 95},
    …
    {"ICULOS": 8, "O2Sat": 94, "MAP": 66, "Lactate": 3.4}
  ] }
  • One object per hour, ICULOS going up by exactly 1. An empty hour is just {"ICULOS": n}.
  • Raw values only. A missing field or null means not measured.
  • Label, unit codes, hospital ID or unknown fields get a 422.

Why the latest hour alone is not enough

  • X__last and X__hours_since_seen need the last time each value was measured. For a lab that can be a day ago.
  • mean_6h, std_6h, change_6h and observations_6h need the previous six hours.
  • The 6-hour alert cooldown needs to know when the last alert fired.

Alternative not built

The server could keep each stay in the DynamoDB table the CloudFormation stack already creates, and the caller would send only the new hour. That needs idempotent writes, out-of-order handling, retention rules and a parity test against the stateless path.

08:00 request for bed 4, end to end

  1. The chart system signs a request with hours 1–8 for bed 4 and sends it to the function URL.
  2. Lambda checks the IAM signature; an unsigned or unauthorised request gets 403.
  3. A warm environment already has the model; a cold one downloads it from S3 and checks its SHA-256 first (about 2 s).
  4. The app validates the JSON, builds the 276 features for hours 1–8, scores them and applies the alert rule.
  5. Hour 8's probability and new_alert go back. Nothing is stored; logs and metrics go to CloudWatch.

Releasing a new model

  1. aws_deploy.sh train: a spot training job selects on validation and registers @candidate in the MLflow App.
  2. The team compares runs in the MLflow UI; promote --reviewed-by moves @production.
  3. publish copies that version to s3://…/models/vN/ and prints its SHA-256.
  4. serve updates the stack with the new S3 URI and hash; new Lambda environments load the new model.
  5. Rollback: promote the previous version, publish, serve.

Roughly $2–5 a month idle plus cents per training run (estimate in docs/aws-serverless.md).
